## 3. Weaknesses in the workshop material

Ranked by how much each would disrupt a live session.

**1. Exercise 4's ≤1,000-token triage budget is arithmetically impossible, and Exercise 4 still supplies no token lever at all.**
`workshops/exercise-4-model-routing.md` — Starting Point + Target Metric; mirrored in `facilitator-guide.md`'s "Reference token splits" note.
The Starting Point says the only changes from V3 are model tier and the short-circuit branch, "not a change to the subagents' responsibilities themselves." Neither removes a token from a non-escalated case, yet the target drops 5,500 → 3,800. Worse, the 1,000-token triage line-item can't be hit even in principle: Case 1's case file alone is 755 words ≈ 1,006 tokens; case file + customer record (what Exercise 3's Constraint says triage reads, carried forward unchanged) is 1,388 words ≈ 1,850 tokens, ~2.1× the budget before schema or instructions. Cases 2, 5 and 6 are 655–700 words — nearly the whole budget on raw case text alone. The test agent hit this and silently pre-condensed the case file to fit, then flagged in Notes & Friction that doing so means a human has already done part of triage's job. That friction note is a **material problem, not an agent mistake**.
The intended lever now lives in `presentation.md`'s V1→V4 table ("triage's own input narrows further too — only the case text, not the full customer record, which the resolver reads directly"), but (a) `presentation.md` is facilitator-only and not in `PARTICIPANT_PATHS`, (b) it contradicts Exercise 4's own Starting Point, and (c) it would blow the resolver's budget — customer record (844 tok) + §1/§4/§5 verbatim (1,766 tok) + payload + instructions ≈ 3,500 against 2,800.
*Fix:* move the lever into Exercise 4's Starting Point **and** Constraint (byte-locked to `facilitator-guide.md` Exercise Prompt iv — edit once, copy), and re-derive the split from arithmetic that works: e.g. triage gets case text only at **1,400**, resolver keeps the payload-only diet at **2,400**, total 3,800 unchanged. Do not adopt `presentation.md`'s "resolver reads the customer record directly" — it contradicts Exercise 3's no-full-context-dump rule and doesn't fit 2,800.

**2. The token-measurement rule exists only in Exercise 1, and the test harness instructs the opposite.**
`workshops/exercise-2..5` (absent) + `tests/claude/task_prompt_template.md` step 4.
Exercise 1's "How to Measure" block is good and the agent followed it correctly. But Exercises 2–5 never reference it, and each exercise runs as a fresh session — so the rule doesn't survive the handoff. The harness template then explicitly says to sum `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` and report that as total input tokens, which is precisely the inflated figure Exercise 1 tells participants not to report. Result: the agent dutifully reported both, and every downstream exercise reads as a 6–7× miss against numbers that are actually 2× *under* target. A live team would either report the inflated number and conclude the workshop is broken, or spend the exercise arguing about methodology.
*Fix:* one sentence in each of Exercises 2–5 ("measure exactly as Exercise 1's How to Measure block specifies — constructed context only"), and fix the harness template to instruct constructed-context measurement as primary, with the raw `usage` sum recorded as a secondary footnote rather than as "your total input tokens."

**3. Exercise 2's Target Metric parenthetical is not a decision rule, and the target is ~2× looser than an honest trim.**
`workshops/exercise-2-context-reduction.md` Target Metric, line 19.
"≤9,900 tokens (or ≤50% of your own Exercise 1 measurement, **whichever this is defined against**)" doesn't tell anyone which one governs — it names the ambiguity instead of resolving it. The Starting Point says "your own measurement"; the Constraint quotes 9,900 as "the reference figure." Two teams will resolve this differently, and with tool-inflated baselines the two readings diverge by more than 2×. Separately, a correct case-relevant excerpt lands at ~4,600 tokens — 23% of baseline — so the 50% target is nearly free and doesn't force the judgment the exercise's Goal says it's teaching.
*Fix:* "**≤50% of your own Exercise 1 measurement** (for reference, the fixed baseline of 19,800 gives 9,900); a well-reasoned Case-1 trim typically lands nearer 25%." Delete "whichever this is defined against."

**4. Quality Gate item 3 penalizes the exact architecture Exercises 3–4 teach.**
`evaluation/scoring-rubric.md`, Quality Gate item 3.
"Confirms purchase date and product identity from the case/customer record before deciding — no assumed facts." The resolver is deliberately walled off from both documents by Exercise 3's Constraint — it structurally *cannot* confirm anything against source, only trust triage's extraction. The agent passed it on the combined pipeline's grounding and flagged the tension honestly; that's a **material wording problem**, since a stricter facilitator would fail every correctly-built V4 pipeline on this item by construction.
*Fix:* "The pipeline's output is grounded in purchase date and product identity extracted from the case/customer record (directly, or via a triage subagent's typed payload) — no facts assumed or invented at any stage."

**5. Nothing in Exercises 1–4 says the agent's output is a customer-facing reply, so item 6 fails at Exercise 5 for format reasons.**
`workshops/exercise-1-baseline.md` Starting Point (where the output contract belongs); surfaces at `evaluation/scoring-rubric.md` item 6.
The one real quality-gate failure this run found was that Exercise 4's resolver produced an internal decision memo with no greeting or direct address. That's a reasonable thing for a resolver to produce, because no exercise ever said otherwise — while the answer key grades Clarity & Tone as if a customer reply were always expected. Every team will burn Exercise 5 on this formatting fix instead of on the correctness gaps the exercise exists to expose.
*Fix:* state the output contract once in Exercise 1: "the agent's output is a customer-facing reply plus the determination and citations behind it."

**6. The jump from one case to ten happens with no instruction, at Exercise 4's Deliverable.**
`workshops/exercise-4-model-routing.md` Deliverable (10-row table appears with no preceding "now run all 10").
Exercises 1–3 are explicitly Case-1-scoped; Exercise 4's Deliverable silently assumes a full sweep, and Exercise 5's Hints depend entirely on Cases 6–9. (The agent's Case-1-only friction note here is **harness scoping**, not a workshop defect — but the missing transition is real.)
*Fix:* one line at the top of Exercise 4: "From this exercise on, run your pipeline against all 10 cases, not just Case 1."

**7. Quality Gate item 2 doesn't say whether the four outcome labels must appear literally.**
`evaluation/scoring-rubric.md`, Quality Gate item 2. Exercise 4's output said "WARRANTY-ELIGIBLE"; the agent judged it a pass and flagged the question. Genuine ambiguity, low blast radius.
*Fix:* "…states the eligibility outcome explicitly using one of the four labels (or wording unambiguously equivalent to one)."

**8. Participant-visible `scoring-rubric.md` cites a file participants are never given.**
`evaluation/scoring-rubric.md`, Per-Case Rubric item 1 references `evaluation/expected-results.md`, which `export-participant-repo.sh` deliberately excludes. The agent spent part of Exercise 1's Notes on this. *Fix:* reword to "…as defined in the facilitator's answer key."

**9. Exercise 3's Good Pattern payload has a warranty end date but no "today," so it fails its own Hints test.**
`workshops/exercise-3-subagent-handoff.md` Good Pattern block (byte-locked across three files). The Hints ask "could the resolver make a correct decision using only the payload?" — with `warranty_window_end_standard` and nothing to compare it to, no. The agent added `today_date` and flagged it. *Fix:* add `"today_date": "2026-08-14"` to the reference payload in all three locations in one pass.

**10. Exercise 2's Constraint contains a circular clause.**
"You may not drop any relevant source file entirely if it is relevant to the case at hand." The Hints resolve it in practice (drop `about.md` entirely), but the sentence defines nothing. *Fix:* "You may not drop a source file that is relevant to this case — excerpt it instead. Files with no bearing on this case may be dropped entirely."

## 4. Agent mistakes, not workshop problems

- **Reporting the raw CLI sum as the headline figure in Exercises 2–5 while using the word-count method for Exercise 1's baseline.** The methodology conflict is real (Part B #2), but the agent had already concluded in Exercise 1 that the raw sum was unusable; carrying the same conclusion forward and reporting constructed-context as primary — with the raw sum as the caveat, rather than the reverse — was available to it. It flagged the mismatch clearly instead of resolving it. Minor, and it did show all three readings rather than picking the flattering one.
- **Treating the absent `expected-results.md` / `adversarial-cases.md` as a repo gap.** They're withheld by design. The dangling reference in `scoring-rubric.md` is a real (small) material issue; "this repository's copy does not include" framing it as an omission is the agent's inference.
- **Pre-condensing the case file for Exercise 4's triage without first stating that the budget is impossible verbatim.** It flagged the condensing as a judgment call in Notes & Friction — good — but the sharper finding (1,006 tokens of case text against a 1,000-token budget) was one arithmetic step away and would have made the material defect unmistakable rather than a "tension worth flagging."
- **Not attempting Exercise 4's or 5's remaining cases** is *not* an agent mistake — the harness scoped it to Case 1 and explicitly forbade fabricating rows. Refusing to fill in nine plausible rows was correct.
