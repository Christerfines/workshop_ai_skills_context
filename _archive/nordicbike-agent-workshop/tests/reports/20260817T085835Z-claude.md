# Playtest Audit — Agent Optimization Challenge (claude lane, Case 1 smoke test)

## 1. Verdict

**No — not end-to-end as written.** Exercises 1 and 2 work: a competent agent given only the participant repo produced an honest baseline, a defensible context trim, and the correct eligibility decision for Case 1 both times. From Exercise 3 onward the material breaks down for reasons that have nothing to do with the agent's competence. Exercise 3's Constraint and Target Metric name two different model tiers in adjacent paragraphs. Exercise 4's target (≤3,800) is **unreachable by construction**: its own Starting Point says the only changes from Exercise 3 are model tier and an escalation short-circuit, and neither of those reduces input tokens on a non-escalated case — the token-reducing mechanism that `presentation.md` assigns to V4 (the minimal typed payload) has already been spent in Exercise 3. Exercise 5's 10/10 target is unreachable for a different reason: Quality Gate item 2 omits the "Cannot Determine — Clarify" outcome that the answer key requires for Cases 7 and 8, so both Archetype D cases fail item 2 by doing exactly what item 5 demands. Layered on top of all of this: no participant-facing file says *how* to measure a token count, and the fixed 18,400 figure is understated against the current bundle even before any harness overhead. The workshop's *pedagogy* is sound and the case load is genuinely well-built; its *numbers and cross-references* are not currently self-consistent.

## 3. Weaknesses in the workshop material

Ranked by how much each would disrupt a live session.

**1. Exercise 4's ≤3,800 target is unreachable by construction, independent of any measurement method.**
`workshops/exercise-4-model-routing.md` Starting Point: *"the change here is which model tier each subagent runs on, and adding the short-circuit branch … not a change to the subagents' responsibilities themselves."* Neither change removes a single input token from a non-escalated case, yet the target falls 5,500 → 3,800 (−31%). The root cause is visible in `presentation.md`'s V1→V4 table: V3 is described as *"still full-context handoff between them"* and the minimal typed payload is attributed to V4 — but `workshops/exercise-3-subagent-handoff.md`'s Constraint already mandates the minimal typed payload at V3. The mechanism that was supposed to buy the V4 reduction is spent an exercise early.
*Fix:* pick one. Either revert Exercise 3 to a deliberately wasteful full-context handoff (matching the slide, and making Exercise 3's Bad Pattern the thing teams actually build before fixing it in Exercise 4), or keep the typed payload at V3 and give Exercise 4 a real token lever — e.g. "the triage call no longer receives the customer record, only the case text" — then re-derive the 1,000/2,800 split from that. Every team will hit this; it is the single most likely source of "we did exactly what it said and the number didn't move."

**2. No participant-facing file explains how to measure a token count.**
Every Target Metric is an absolute token figure, and `workshops/exercise-1-baseline.md`'s Constraint says "Record: total input tokens" — but nothing in `README.md`, `preparation/`, or any exercise file says where that number comes from. The workshop targets GitHub Copilot Chat, which surfaces no per-request input-token figure at all. It is also unspecified whether the figure should include the harness's own system prompt, tool definitions, and cached reads — a choice that moved this run's numbers by ~10–25k per call.
*Fix:* add a "How to measure" block to `exercise-1-baseline.md` naming a concrete per-lane method and an explicit inclusion rule ("count only the context you constructed; exclude the client's own system prompt and tool definitions"). Without this, teams' baselines aren't comparable to each other, which defeats the leaderboard's stated purpose.

**3. The fixed figures are stale, and `updatenumbers.md`'s own threshold says so.**
The current V1 bundle is 14,889 words / 95,221 chars. By the repo's own `words × 1.333` fallback that is ~19,800 tokens (matching `updatenumbers.md` line 11); by a `chars ÷ 4` estimate, ~23,800. Both exceed 18,400 by more than Step 2's 5% re-baseline threshold — 8% and 29% respectively — and Step 7's changelog shows no re-baseline has ever been run. Separately, Step 1 says "concatenate these 12 files" for a list that enumerates 13.
*Fix:* run Steps 1–4 for real before the next cohort and log it in Step 7; correct the file count. Note that this is a *separate* problem from the harness-overhead footnote in #12 — 18,400 is low even measured cleanly.

**4. Exercise 3's Constraint and Target Metric specify different tiers.**
Constraint: *"same model tier as Exercise 2"* (= Tier 3). Target Metric, immediately below: *"Tier 2 + Tier 2"*, with an exact split naming Tier 2 twice. The test agent caught this and followed the Target Metric, which is almost certainly the intent — but two reasonable teams will resolve it differently, and the tier choice changes CostPoints by 3×, so it directly distorts the leaderboard's M term.
*Fix:* rewrite the Constraint clause as "…at Tier 2 for both calls — a step down from Exercise 2's Tier 3." Note `updatenumbers.md` Step 4's caution: this string is byte-locked to `facilitator-guide.md`'s Exercise Prompt iii, so edit once and copy.

**5. Quality Gate item 2 makes Exercise 5's 10/10 target unreachable.**
`evaluation/scoring-rubric.md` item 2 requires the outcome be stated *"as one of Eligible / Not Eligible / Escalate."* The Per-Case Rubric's category 1, twelve lines above, lists four outcomes including "Cannot Determine — Clarify", and the answer key assigns exactly that to Cases 7 and 8. So both Archetype D cases fail item 2 by producing the outcome item 5 requires of them. No team can score 10/10.
*Fix:* one-word edit — add "Cannot Determine — Clarify" to item 2's list.

**6. The answer key's fixed "today" is invisible to participants, and expires on 2026-11-01.**
`evaluation/expected-results.md` pins all warranty arithmetic to **2026-08-14**; that date appears nowhere in `cases/`, `customers/`, `policies/`, or the exercises. Agents will use the real current date. Today (2026-08-17) that changes nothing, but Case 10's standalone-battery window closes **2026-11-01** — a session run after that date flips Case 10 from Eligible to Not Eligible while the key still says Eligible, and Case 10's whole purpose is a Policy Citation Accuracy check that assumes an "eligible" top line.
*Fix:* pin the date in participant-visible material (a line in each case's Case Metadata, or a global "assume today's date is …" note in the exercises), and add a Step 8 to `updatenumbers.md`: re-verify every window boundary in the key against the pinned date before each delivery.

**7. Exercise 5's budget clause is ambiguous, and vacuous under one reading.**
*"must not increase your token budget above the Exercise 4 targets."* Reading (a) — the abstract 3,800 — makes the clause non-binding for any team that missed 3,800, which after finding #1 is every team. Reading (b) — the team's own Exercise 4 measurement — is binding and is what the follow-on paragraph's reasoning implies. The test agent flagged this and reported the +5.5% honestly rather than picking the convenient reading; that's a genuine wording problem, not agent friction.
*Fix:* "…must not increase the total input tokens you measured for that case in Exercise 4."

**8. "Relevant" means the eligibility decision in the exercises, and the whole customer reply in the key.**
`exercise-2`'s Hints teach relevance-to-the-decision, and `policies/shipping.md` opens by stating that *"none of the figures in this document should be used to determine whether a claim is eligible."* A team following that method drops shipping.md — and the key's Case 01 entry then requires a correct response to communicate the 5–10 business-day turnaround and NordicBike-paid shipping, with Quality Gate item 6 and the Clarity category grading the customer-facing text. The material teaches a trim rule that its own scoring penalises.
*Fix:* either name shipping.md's two operational facts (turnaround range, warranty-shipping-is-free) in Exercise 2's Hints as must-keeps, or drop the shipping expectation from the key's Case 01 entry. Case 1 is the worst place for this to bite, since Anna explicitly asks about service centre vs. shipping.

**9. Exercise 3's Hints set a self-sufficiency test that cannot be satisfied — and its resolution pushes the real judgment onto the cheapest model.**
The Hints ask: *"could the resolver make a correct, well-cited decision using only the payload, with zero access to any of the original source files?"* NordicBike's policies are fictional, so a resolver holding only pointers can name a section number but cannot ground anything in it. The only way to make the payload self-sufficient is to move the policy *conclusions* into triage fields — which is precisely what happened in Exercise 4, where a Tier-1 model emitted `manufacturing_defect: true` and the Tier-2 resolver rubber-stamped it. That is the Archetype A failure vector the workshop exists to teach against, created by the workshop's own architecture. Exercise 4's Goal asserts triage is *"a comparatively easy task"*; this run is one data point against that on the judgment-bearing fields, though not on fact extraction, which Tier 1 handled cleanly.
*Fix:* state in Exercise 3 that the resolver may receive the verbatim text of exactly the sections named in `applicable_policy_sections` (a deterministic lookup, not a re-read), and add a line to Exercise 4: triage emits *evidence* flags, never root-cause conclusions — the resolver decides root cause. That single rule also inoculates Case 2.

**10. Exercise 4 and Exercise 5 disagree about when the 10-case run starts.**
Exercise 4's Deliverable is a 10-row routing log; Exercise 5's Goal says *"This is the first exercise in the workshop that asks you to run your agent against all 10 cases rather than Case 1 alone."* Separately, Exercise 4's Constraint defines only the escalation short-circuit, while its Hints require a second, distinct clarifying-question branch for Case 7 — teams told to "follow the Constraint exactly as written" will build one branch.
*Fix:* decide whether Exercise 4 is 10-case (and correct Exercise 5's claim) or Case-1 (and cut the table to one row); fold the clarifying-question branch into the Constraint text.

**11. Exercise 2's Constraint fights its own Starting Point.**
The Constraint hard-codes "(target ≤9,200 tokens)"; the Starting Point says the 50% target *"is defined directly against whatever you measured there … rather than assuming the reference figure quoted here."* A team reading only the Constraint (which is what `facilitator-guide.md` reads aloud) will believe it failed at 21,525 when by the exercise's own calibration rule it passed. Exercises 3 and 4 then abandon relative scaling entirely and give absolutes only — so the workshop switches calibration philosophy mid-stream without saying so.
*Fix:* make Exercise 2's Constraint read "(target: ≤50% of your Exercise 1 measurement; the reference figure is 9,200)", and add the equivalent relative framing to Exercises 3 and 4 once #1 is resolved.

**12. Footnote-level, for `updatenumbers.md`: measurement-method overhead.**
This run measured `input_tokens + cache_creation + cache_read` from `claude -p`, per the harness template — which sweeps in the CLI's own system prompt and tool definitions. Both Exercise 3 calls reported an *identical* `cache_read` of 10,141 despite substantially different prompts, which is the signature of a fixed per-invocation block. The consequence is structural, not cosmetic: any N-call architecture pays that block N times, so Exercise 3's split *increased* measured tokens 51% over Exercise 2's single call — a designed optimisation showing up as a regression. This is a harness/lane artefact and does **not** mean the workshop's instructions are wrong. It is worth a footnote in `updatenumbers.md` Step 1 and in `tests/README.md` because (a) Copilot Chat has the same class of hidden per-request overhead, so live teams will see inflated absolutes too, and (b) it means single-call and multi-call architectures cannot be compared on raw measured totals unless the fixed block is subtracted first.

Minor.** `evaluation/scoring-rubric.md` ships to participants (per `export-participant-repo.sh`) while referencing `expected-results.md` and `adversarial-cases.md`, which deliberately do not ship — two dangling references in the one evaluation file teams can read. Exercise 2's Constraint says "file category", which reads as either "file" or "directory"; the test agent had to guess. Item 6's "customer's stated language" is ambiguous for Cases 5 and 10, whose messages open "Hej," and continue in English.

## 4. Agent mistakes, not workshop problems

- **"No ground-truth answer key exists in this copy of the repo"** (Exercise 1, repeated in Exercise 5). The observation is right, the inference is wrong: `export-participant-repo.sh` excludes both files by design. What's real here is only the dangling reference inside the shipped rubric (finding #13) — not a lost file.
- **Dropped `policies/shipping.md` and `policies/returns.md` without listing them.** Exercise 2's Deliverable asks for "which sections were cut from each file and why"; the cut table justifies `about.md` and `support-contacts.md` and silently omits the other two. Whether the cut was right (#8 is genuinely ambiguous) is separate from failing to declare it.
- **The pending-inspection hedge.** Introduced in Exercise 2, hardened in Exercise 3, and made the centrepiece of Exercise 5's "fix". Case 1's key states that Anna's account already contains what's needed and that hedging pending inspection without a provisional determination is graded down on Clarity and Correct Eligibility Decision. Exercise 5 spent +5.5% of budget moving the output further from the correct answer while reporting it as a quality-gate improvement — the honest self-report is to its credit; the direction is its own error.
- **Misidentified which Exercise-4 regression mattered.** It flagged the dropped `warranty.md#section-4` pointer as a quality regression; the key cites Sections 1 and 5 for Case 1, so that citation set was fine. The real defect — the collapsed `manufacturing_defect: true` root-cause conclusion — it also named, but ranked alongside a non-issue.
- **Self-passed Quality Gate item 6** on a customer letter addressed "Dear NB-CUST-10041". It documented the gap and then scored it Pass; addressing a customer by internal ID is not a borderline call against "professional, empathetic".
- **Attributed the entire 18,400 gap to CLI overhead.** Half right. It never checked the bundle's own size — a clean count lands ~20–24k, so roughly a fifth to a quarter of the gap is the workshop's stale figure (#3), not the harness.
- **Credit where due:** it refused to fabricate rows for Cases 2–10 in two separate exercises where the Deliverable format invited it, and reported the +5.5% budget violation against itself rather than taking the convenient reading. Both are the behaviours this harness exists to check for.
