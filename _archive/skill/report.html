NordicBike Agent Optimization Challenge — Participant Report

Case load: 10 cases · Baseline reference: 19,800 tokens, 1 call, Tier 3 · Assumed date: 2026-08-14

Model Tiers

Tier 1 — Fast/cheap
Cost weight: 1 / 1,000 tokens.
Used for: cheap, high-volume, low-complexity tasks — e.g. triage/fact-extraction from a case file. Doesn't need to weigh evidence or reach conclusions.
Tier 2 — Balanced
Cost weight: 4 / 1,000 tokens.
Used for: the resolver call — applying policy, weighing root-cause evidence, and reaching the eligibility decision. Needs stronger reasoning than triage.
Tier 3 — Frontier
Cost weight: 12 / 1,000 tokens.
Used only in the V1 naive baseline and V2 (single-call, unsplit architecture) — the most capable and most expensive tier, used because the whole task (read everything + decide) is dumped on one call.

Why the Token Count Drops V1 → V4

StepTokensWhat actually changed
V1 → V219,847 → 1,562 (−92%)Same 1 call, same Tier 3 — only the input content changed. V1 dumps every KB file in full (all 5 products, all 4 policies, full customer record, company pages). V2 keeps only the excerpts the decision actually depends on (relevant product facts, 3 warranty sections, 2 shipping facts, ID-only customer facts) and drops files with no bearing on the case (company/about.md, other products, returns.md) entirely. This is pure context curation — no architecture change.
V2 → V31,562 → 1,470 (≈ flat)The call count changes (1 → 2) but total tokens barely move, because the same curated facts are now split across a triage call and a resolver call instead of one call — no new content is added, and the handoff between them is a small typed JSON payload (facts only), not a second copy of the source files. The token count is flat here because V2 was already lean; the real gain in this step is architectural (separable, reusable subagents), not a token cut.
V3 → V41,470 → ≈3,800 budget (case-by-case), but cost drops sharplyTwo things move in opposite directions: (1) triage's own input narrows further — it now reads only the case text, not the full customer record (the resolver reads that directly instead), which is a genuine token cut; (2) the fixed architecture budget in the exercise (2,500+3,000=5,500 for V3 vs 1,400+2,400=3,800 for V4) is a larger allowance than what this particular clean case needed, so raw token totals aren't directly comparable case-by-case — the real lever in this step is tier routing: triage moves from Tier 2 (weight 4) to Tier 1 (weight 1), so the same-sized triage call now costs roughly a quarter as much, even where token counts are similar. V4 also adds the escalate/clarify short-circuits, which skip the resolver call entirely for 4 of the 10 cases — cutting cost to near-zero for those cases.

Summary of the four levers, one per exercise: V1→V2 = less content (context curation). V2→V3 = same content, split into reusable calls (subagent handoff). V3→V4 = cheaper model per call (tier routing) + skip calls entirely when possible (short-circuiting). Token count alone under-tells the V3→V4 story — the cost-weight table above is what actually explains most of that step's savings.
